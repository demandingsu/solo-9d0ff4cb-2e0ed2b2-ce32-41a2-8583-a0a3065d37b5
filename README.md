# 矿石配料反推与异常定位

由成品四项元素含量反推三种原矿的质量占比，定位配料异常；对无法唯一归因的样本，
可从候选元素中选出最值得补测的（至多两项）元素组合。技术栈：FastAPI + SQLite
（标准库 `sqlite3`）+ Jinja2 页面，可实际用 Docker Compose 启动。

## 启动

### Docker Compose（推荐）

```bash
docker compose up --build
```

浏览器打开 <http://localhost:8000>。数据库落在名为 `ore-data` 的 Docker 卷中，
容器重建后数据仍在。`docker compose down -v` 会连数据一起删除。
旧版本创建的数据库在首次启动时会自动迁移（`input_versions` 增加 `candidates`
类型、新增 `plans` 表），已有输入与报告不受影响。

### 本地直接运行

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

默认数据库路径为 `data/app.db`，可用环境变量 `ORE_DB_PATH` 覆盖。

## 页面操作

1. **上传输入**：选择“基准 CSV”（三种原矿 × 四项元素）、“成品 CSV”
   （样本编号 × 四项元素）和/或“候选元素 CSV”（同样三种原矿 × 至多 8 项候选元素）。
   每次上传都会**整版替换**所选的输入；未选择的输入保持不变。
   多类文件可以一次提交，此时在同一事务里一起替换。
   候选元素文件的原矿名称须与当前基准完全一致（行顺序不限，按名称对齐），
   且候选元素不能与基准已测元素重名。
2. **计算占比**：点击按钮，对当前基准与成品输入中的每个样本求解。报告发布后页面显示
   占比、预测值、残差与 SSE。
3. **报告状态**：基准或成品被替换后，上一份报告立即显示“已过期”，但仍可查看，
   并分别标明基准/成品哪一侧与当前输入不一致。
4. **补测计划**：报告未过期且存在“无法唯一确定”的样本时，选择样本并计算，
   找出能让其全部最优占比仅剩一组的**最少**候选元素组合（最多两项，列出所有
   并列组合；无解则说明原因）。计划保存时绑定报告与基准/成品/候选文件版本；
   任一来源变化后旧计划标记“已过期”，但仍可查看。
5. **导出**：报告的 CSV 导出包含占比的 min/max 列；三类输入也可以分别导出为 CSV。

示例文件位于 `sample_data/`（`baseline.csv`、`samples.csv`、`candidates.csv`）。

### CSV 格式

基准 `baseline.csv`（第一列表头任意，但必须恰好 3 行原矿、4 个元素列）：

```csv
ore,Fe,SiO2,Al2O3,CaO
A,62.30,3.90,2.10,1.20
B,68.50,2.50,1.10,0.80
C,55.20,6.20,3.40,2.10
```

成品 `samples.csv`（第一列表头任意，样本编号不能重复，元素列按名称与基准匹配）：

```csv
sample_id,Fe,SiO2,Al2O3,CaO
S-1001,62.74,3.71,2.02,1.13
```

候选元素 `candidates.csv`（恰好 3 行原矿、1~8 个候选元素列；原矿名称须与当前
基准一致，顺序不限；元素名不得与基准元素重复）：

```csv
ore,P,TiO2,MnO
A,0.020,0.150,0.300
B,0.008,0.090,0.180
C,0.035,0.240,0.120
```

校验规则：UTF-8 编码（接受 BOM）、空行忽略；每格必须是**有限非负数**
（支持 `1.5`、`1e-3` 这类十进制/科学计数法，拒绝 `nan`/`inf`/负数/其它字符）；
绝对值须在 `1e-100` 与 `1e100` 之间（防止异常输入把精确整数运算拖垮）；
样本编号必须非空且不重复；列数必须一致；单文件 ≤ 5 MB，成品最多 2000 个样本。

任何一行不合法都会**整体拒绝**该文件，原有输入、旧报告与已有计划不受影响。

## 计算模型与“无法唯一确定”

对每个样本，令 `A` 为 4×3 的基准矩阵（列为三种原矿），`y` 为四项实测含量，
求解

```
min  || A w - y ||²   s.t.  w ≥ 0,  w₁ + w₂ + w₃ = 1
```

这是一个带单纯形约束的最小二乘问题。实现上枚举单纯形的 7 个非空面（3 个顶点、
3 条边、1 个三角形），在每个面的相对内部精确求出驻点集合，再比较各面 SSE 取全局最小。
所有中间运算使用 `fractions.Fraction` **精确有理数**：

- 比例的“是否唯一”是**精确判定**，不是浮点阈值判断；
- 不存在“两个同样最优解因舍入误差被当成一个”的情况；
- 唯一解时输出精确比例（如 `19229/20780`），显示时再转成小数。

当最优解不唯一（例如两种原矿元素含量完全相同、或基准矩阵秩小于 3）时，报告
**不会任取一组**：占比、预测值与残差都以该最优解集合的精确可达区间（min ~ max）
呈现，并标记“无法唯一确定”。CSV 导出同样如此——非唯一样本的 `*_weight` 单元格
留空，只给 `*_weight_min` / `*_weight_max`。逐矿占比区间只是范围，
**不能把各矿区间端点随意拼成一组配方**；补测计划展示的是最优集合的端点
（极点），其中每一个都是真实可达的最优配比。

## 补测计划的判定逻辑

设当前最优占比集合为 Ω（非单点），候选元素 `e` 在三种原矿上的含量为行向量 `c_e`。
计划的假设（页面上同时声明）：**补测值精确且遵循原混合模型**——样本的真实占比
`w*` 是 Ω 中的某一组，补测元素 `e` 的实测值恰好等于 `c_e·w*`。此时新问题的
目标函数为

```
f_new(w) = ||A w - y||² + Σ_e (c_e·(w − w*))²
```

对 `w ∈ Ω`，第一项等于旧最优 SSE，等号成立当且仅当所有补测元素取值与 `w*`
一致；对 `w ∉ Ω`，第一项已严格更大。因此补测后的最优集合是
`{w ∈ Ω : c_e·w = c_e·w* ∀e}`：只要所选元素把 Ω 中任意两组占比区分开，
补测后最优占比必唯一（即真实占比 `w*`）。

“区分开”的判定是精确的：取 Ω 的端点（极点），其差异方向张成 1 维（线段）或
2 维（整个三角形）的子空间；所选元素行向量在该子空间上的限制秩等于子空间维数时，
它们就能区分所有最优占比。实现枚举所有 1 项、2 项组合，取能使最优占比唯一的
**最少**项数，并列出该项数下的**全部**并列组合。若不超过两项无解，则给出原因
（由于差异子空间至多 2 维，此时即使补测全部候选元素也无法区分，需更换或增加
候选元素）。该结论有端到端验证：测试对每个最优占比模拟精确补测值并求解增广
问题，确认最优解收敛到该真实占比。

## 上传与计算交错时的发布规则

- 上传：整份文件解析并校验通过后才进入数据库事务；多类输入在同一事务内替换，
  并且 `input_versions` 上有“每个 kind 只能有一个 `is_current`”的唯一索引。
- 计算（报告与补测计划相同）：开始时用**同一读事务**取出当前输入（与最新报告）
  的快照（含版本号），整个计算只依赖该快照。
- 发布：`BEGIN IMMEDIATE` 事务内先复查“这些版本号是否仍是当前版本、报告是否仍是
  最新”，再插入报告/计划。若期间有输入被上传替换或有新报告发布，则**丢弃**本次
  结果并提示重新计算，绝不发布与当前来源不符的结果。
- 报告/计划与版本：只存版本号；页面每次读取时用当前版本号对比，得出是否过期。
  因此“过期”状态永远是实际状态，不会因为漏改标志位而错误。过期内容仍可查看。
- 写入失败（磁盘/数据库错误）时页面提示，旧报告、旧计划与其过期状态照常可看。

## 已知限制

- 计算是纯 Python 精确有理数运算，2000 个样本约 7–8 秒；页面显示前 500 行，
  其余通过 CSV 导出查看。
- 页面显示的小数经四舍五入（默认 8 位，占比为百分比）；精确值保存在数据库/JSON
  接口中（以 `分子/分母` 形式给出）。量级极端的值在网页上以科学计数法显示。
- `/api/latest` 返回完整报告（含全部样本的精确值）；2000 个样本时响应约 1.7 MB。
  `/api/plans` 返回全部补测计划（含过期标记）。
- 占比反推仅支持“三种原矿 / 四项元素”的固定规模，与题目要求一致；补测计划
  支持至多 8 项候选元素、每次最多选 2 项。
- 补测计划的结论依赖“补测值精确且遵循原混合模型”的假设；若真实样本不满足
  该假设（例如补测元素上存在未建模的误差），唯一性结论不成立。
- 候选元素文件在上传时按当时基准校验原矿名称；之后基准被替换会导致两者不一致，
  此时制定计划会被拒绝并提示重新上传（计划本身绑定双方版本，过期后仍可查）。
- 单进程内用线程锁串行化写操作；多 worker 部署时依赖 SQLite 自身的
  `BEGIN IMMEDIATE` 与唯一索引保证一致性（未针对多 worker 做压力验证）。
- 页面无用户认证，默认假设在内网/可信环境使用。
